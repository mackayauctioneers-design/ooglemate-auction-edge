# CarBitrage Platform Architecture & Dealer Roadmap

**Author:** Manus AI
**Date:** March 01, 2026

## 1. Introduction: The Two-Tier Vision

This document outlines the architecture of the CarBitrage platform, designed to serve two distinct user tiers. This model is foundational to the business strategy of operating a premier, data-driven vehicle wholesale buying operation while simultaneously offering a scalable, subscription-based intelligence product to other dealers.

- **The Operator Tier (Your View):** An all-access command center for running the core CarBitrage buying operation. This tier provides unrestricted access to raw data feeds, enrichment pipelines, scoring engines, and proprietary intelligence. The primary goal is to maximize buying advantage through superior information and tooling.

- **The Dealer Tier (Subscriber View):** A polished, productized service for subscribed dealers. This tier provides curated, actionable intelligence derived from the operator's powerhouse. The user experience is focused on simplicity, delivering high-value buying opportunities without exposing the underlying mechanics or proprietary data.

## 2. Platform Architecture

The platform is built on a unified Supabase backend, with access levels managed by a robust role-based security model. The frontend is a React/TypeScript application that renders a different user experience based on the authenticated user's role.

| Component | Operator Tier (You) | Dealer Tier (Subscribers) |
| :--- | :--- | :--- |
| **Primary Interface** | `/operator/*` routes | Root `/` routes (e.g., `/trading-desk`) |
| **Authentication** | `OperatorGuard` (requires 'admin' or 'internal' role) | `RequireAuth` (requires any authenticated user) |
| **Data Access** | Full read/write to all tables | Row-Level Security (RLS) scopes data to their `dealer_id` |
| **Core Features** | Pipeline Health, Morning Brief, OogleBot (full), Buy Intelligence, Fingerprint Explorer, Data Sources | Trading Desk (simplified), My Sales, Closed Deals, OogleBot (simplified), Hunts & Alerts |
| **Intelligence View** | Raw data, scoring logic, margin calculations, WOVR flags, guide prices | Curated "BUY"/"WATCH" signals, match alerts, benchmark data (no raw scores) |

### Core Infrastructure (Shared)

- **Supabase Backend:** PostgreSQL database, Edge Functions, and Authentication.
- **Enrichment Pipeline:** A series of automated functions (`auction-detail-enricher`, `manus-auction-webhook`) that process raw auction listings. Operators see the pipeline itself; dealers see the enriched results.
- **`vehicle_listings` Table:** The central source of truth for all vehicle data. This is the primary asset generated by the operator tier and consumed by the dealer tier.
- **`dealer_specs` Table:** Defines the buying criteria for all users. RLS ensures dealers can only access and manage their own specifications.
- **`hunt_alerts` Table:** Stores generated matches between `vehicle_listings` and `dealer_specs`, forming the basis of the alert system for all users.

## 3. Current State Audit

The audit reveals a strong foundation but identifies key gaps in the dealer-facing product that must be addressed to create a sellable, self-serve platform.

### What's Built (✅)

- **Strong Role Separation:** The use of `OperatorGuard` and a database-level `get_user_role` function provides a secure and clear distinction between operator and dealer access.
- **Powerful Operator Tooling:** The `/operator` section is feature-rich, containing the necessary tools for data ingestion, enrichment, monitoring, and intelligence gathering (e.g., Morning Brief, Pipeline Health).
- **Dealer-Specific Data Scoping:** The database schema correctly links `dealer_specs` and `hunt_alerts` to a `dealer_id`, ensuring data is properly segregated.
- **Basic Dealer UI Components:** Key pages for the dealer experience exist, including a simplified Trading Desk, OogleBot search, and a form for managing `dealer_specs`.
- **Core Alert Infrastructure:** The `hunt_alerts` table and the `alert-notifier` function provide the backbone for delivering match alerts.

### What's Missing (❌)

- **Monetization & Subscription Management:** There are no database tables or infrastructure for managing customer subscriptions, plans, or billing. This is the single largest blocker to creating a sellable product.
- **Self-Serve Onboarding:** The current `AuthPage` is a simple login form. There is no flow for a new dealer to sign up, create a profile, select a plan, and enter payment information.
- **Dealer Settings & Profile Management:** Dealers have no interface to manage their profile, notification preferences (e.g., quiet hours, email vs. push), or view their subscription/billing status.
- **Legacy Push Notification System:** The current push notification system relies on a Google Sheets backend, which is not scalable or robust. This is a critical point of failure for a real-time alert product.
- **Inconsistent Dealer UI/UX:** The dealer-facing sidebar and routing are not fully polished. Some operator-level pages and concepts are still exposed, and the overall experience lacks the clean, focused feel of a commercial product.

## 4. Roadmap to a Sellable MVP

This roadmap prioritizes the features required to launch a Minimum Viable Product (MVP) for the dealer-facing subscription service.

### Phase 1: Solidify the Dealer Core (Immediate Priority)

*Objective: Build the foundational tables and services for a robust, multi-tenant dealer platform.*

1.  **Create `subscriptions` and `plans` Tables:** Establish the database schema to track which dealer is on which plan (`free`, `pro`, etc.) and their current billing status.
2.  **Create `dealer_settings` Table:** Allow dealers to control their experience, starting with notification preferences (e.g., `notify_buy_alerts`, `notify_watch_alerts`, `quiet_hours_start`, `quiet_hours_end`).
3.  **Migrate Push Notifications to Supabase:**
    - Create a `push_subscriptions` table in PostgreSQL.
    - Refactor the `push-subscribe` and `push-send` functions to use this new table, completely removing the Google Sheets dependency.
4.  **Refine the Dealer UI/UX:**
    - Create a dedicated `DealerLayout` to ensure a consistent and clean experience.
    - Refine the `AppSidebar` to only show relevant dealer navigation items (`Trading Desk`, `My Hunts`, `My Sales`, `Settings`).
    - Audit all dealer-facing pages to remove any operator-specific language or components.

### Phase 2: Monetization & Onboarding

*Objective: Enable self-serve sign-up and payment, turning the platform into a commercial product.*

1.  **Integrate Stripe for Subscriptions:**
    - Use Stripe Checkout for a secure, hosted payment and plan selection page.
    - Create a Supabase edge function to act as a webhook handler, listening for `checkout.session.completed` and `customer.subscription.updated` events from Stripe to automatically update the `subscriptions` table.
2.  **Build a Public-Facing Pricing Page:** Create a page at `/pricing` that details the available subscription plans, features, and pricing, with clear calls-to-action that link to the Stripe Checkout session.
3.  **Develop a Self-Serve Onboarding Flow:**
    - Enhance the `AuthPage` to include a "Sign Up" option.
    - After a user signs up via Supabase Auth, guide them through a multi-step onboarding process: 1) Create their `dealer_profile`, 2) Select a plan on the `/pricing` page, 3) Complete payment via Stripe, 4) Land on a "Welcome" page that prompts them to create their first `dealer_spec` (hunt).

### Phase 3: Scale & Intelligence

*Objective: Enhance the value of the dealer subscription with more powerful tools and communication channels.*

1.  **Implement Email & SMS Alerts:** In addition to push notifications, integrate with services like Twilio SendGrid (for email) and Twilio SMS to offer more resilient and configurable alert delivery options in `dealer_settings`.
2.  **Build a Dealer-Facing "My Hunts" Page:** Create a dedicated page where dealers can view all their active `dealer_specs`, see their performance (e.g., number of alerts generated), and easily edit, pause, or delete them.
3.  **Develop a "Welcome" Email Sequence:** Upon sign-up, trigger an automated email sequence that explains how to get the most out of the platform, how to set up effective hunts, and how to interpret alerts.

By following this roadmap, the CarBitrage platform can systematically evolve from a powerful internal tool into a valuable, scalable, and commercially successful intelligence product for the automotive industry.
